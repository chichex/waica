# Spec — Fixed simulation step: the loop advances in whole 1/60 s steps and the Runtime Bridge steps by frames

## Contexto

The engine hands every component whatever wall-clock delta the last frame took: `tick` (`packages/engine/src/game.ts:417-422`) and `resumeRuntime` (`game.ts:408-415`) derive `dt` from the clock with a 0.1 s clamp, and `runFrame` (`game.ts:424-453`) passes that single `dt` to `component.onUpdate?.(dt)`, `updateSceneCamera(dt)` and the host `updateFns`. Euler integration (`platformer-motor.ts:121,133`, `dynamic-body.ts:64-69`), `resolveSolidAxis` sampling and accumulated timers (`state-machine.ts:158`, `clip-player.ts:28`) therefore differ between a 60 Hz and a 144 Hz display, and a hitch plays the world in slow motion. The Runtime Bridge mirrors the problem: `step { dt?, frames? }` accepts any `0 < dt ≤ 0.1` (`runtime-bridge.ts:151-171`, `packages/mcp/src/server.ts:219,400-472`).

The grill `2026-09-12-fixed-timestep` (finalized) fixed the design: one channel at a fixed **Simulation Step** of 1/60 s consumed from an accumulator with a per-frame cap, leftover time dropped; no render interpolation yet; `step { frames }` with no `dt`; the change announced as the `'fixed-step'` bridge capability, never as a protocol bump; no retuning (parity is proven numerically); a general pre-1.0 disclaimer instead of a change note. `CONTEXT.md` (`Simulation Step`), ADR 0014 and the supersession note in ADR 0006 were written during that grill and sit uncommitted in the working tree: they ride with this change's PR.

## Comportamiento esperado

- **CA-1 — One channel, one fixed step.** *(ALTA)* `SIMULATION_STEP = 1/60` is exported from `@waica/engine`. Driving `Game.tick(time)` with synthetic timestamps that advance past t = 1000 ms at a 60 Hz cadence (≈16.667 ms apart) and, separately, at a 144 Hz cadence (≈6.944 ms apart) yields exactly 60 calls to every component `onUpdate`, to `updateSceneCamera` and to every `game.onUpdate` callback in both runs, each call receiving `dt === SIMULATION_STEP`. No code path passes any other `dt` to those three consumers.
- **CA-2 — Accumulator, cap, drop.** *(ALTA)* A pure helper in `packages/engine/src/fixed-step.ts` computes, from a retained remainder `r` and an elapsed `e` (seconds), `steps = min(floor((r + e) / SIMULATION_STEP), MAX_STEPS_PER_FRAME)` with `MAX_STEPS_PER_FRAME = 6`; when the cap is hit the new remainder is 0 (leftover dropped), otherwise it is `(r + e) − steps × SIMULATION_STEP`. Concretely: `r = 0, e = 0.033` → 2 steps, remainder ≈ 0.00033 *[DEVIATION 2026-09-12: 0.033 s holds only one step under this very formula — the test uses `e = 0.034` → 2 steps, remainder ≈ 0.00067; see Desviaciones]*; `r = 0, e = 0.300` → 6 steps, remainder 0; `r = 0, e = 0.005` → 0 steps, remainder 0.005. The 0.1 s clamp no longer exists.
- **CA-3 — No bursts.** *(ALTA)* The first `tick` after `start()` runs 0 steps and renders once; after `stop()`, any gap and `start()` again, the first `tick` runs 0 steps; the first animation frame after `resumeRuntime` runs 0 steps. Both entry points reset the remainder and re-seed the clock.
- **CA-4 — Per-step frame hygiene.** *(ALTA)* In one `tick` that runs two steps: an action pressed before the tick reads `justPressed === true` in exactly one of the two steps (`input.endFrame()` runs after every step); a `loadSceneByName` enqueued by a component during step 1 is applied before step 2 (`flushPendingSceneLoad` runs before every step), so the incoming scene's entities update in step 2 and the outgoing ones do not.
- **CA-5 — Once per render frame.** *(ALTA)* Whether a `tick` runs 0, 1 or 6 steps, `renderer.render`, `ui.setActive`, `audio.setActive` and `audio.updatePlacements` each run exactly once, after the last step. With `simulate = false` a tick runs 0 steps and still renders once.
- **CA-6 — The bridge steps by whole steps.** *(ALTA)* The `step` variant of `RuntimeControlRequest` is `{ operation: 'step'; frames?: number }`. `control({ operation: 'step', frames: 2 })` invokes each `onUpdate` twice with `SIMULATION_STEP`; `metadata()` then reports `frame === 2` and `simulationTime === 2 * SIMULATION_STEP`; after `frames: 60`, `simulationTime === 1` exactly, because `simulationTime` is derived as `frame × SIMULATION_STEP`, never summed. Any `step` request carrying a `dt` property — including `dt: 1/60` — throws `RuntimeBridgeOperationError` with `code: 'runtime-operation-failed'` and a message that names `frames` and the fixed 1/60 s step. `frames` validation (integer 1–600) is unchanged. `RUNTIME_BRIDGE_CAPABILITIES` equals `['click', 'scene', 'fixed-step']`; `RUNTIME_BRIDGE_PROTOCOL_VERSION` stays `1`.
- **CA-7 — Real-time playback shares the accumulator.** *(ALTA)* After `resume`, animation-loop timestamps feed the same accumulator and the bridge's `advance()` fires once per step: one second of 60 Hz timestamps raises `frame` by 60; `pause` followed by `step { frames: 1 }` reports `frame` exactly one higher than at pause.
- **CA-8 — MCP contract.** *(ALTA for schema and validation; BAJA for prose)* `control_runtime`'s input schema has no `dt` property and the `step` branch accepts only the optional `frames`; a call with `dt` fails input validation with a message that names `frames`; the "does not accept" guards of the other operations list `frames` but no longer `dt`; `RuntimeControlInput` in `runtime-service.ts` drops `dt`. The tool description (`server.ts:209`) and `packages/mcp/README.md` (the `step` bullet) state that `step` advances whole 1/60 s Simulation Steps and that `dt` is not accepted.
- **CA-9 — Feel parity.** *(ALTA)* `PlatformerMotor` with default params, grounded, after its jump is triggered and with `jump` held for the whole ascent (no jump cut), stepped at `SIMULATION_STEP`: the apex is 2.217 ± 0.001 u above the take-off height and the body is back at take-off height on the 40th step (0.667 s). A `StateMachine` transition on `timer:0.3` fires on the 18th `onUpdate(SIMULATION_STEP)` and not on the 17th.
- **CA-10 — e2e legs unchanged in outcome.** *(MEDIA)* `scripts/runtime-e2e.mjs` sends every `step` request without `dt` (the five call sites at `:414-416`, `:518-531`, `:638-640`, `:758-759`, `:1134`) and `pnpm test:e2e` passes with every existing assertion untouched — `frame === 3`, `simulationTime === 0.05`, the position and collision assertions.
- **CA-11 — Pre-1.0 disclaimer.** *(BAJA)* The **Status** paragraph of `README.md` and `packages/cli/README.md` (right after the `npx @waica/cli` block) contain the sentence: "Waica is pre-1.0: a minor release may break projects created with the previous one, and individual breaks are not announced until 1.0."

## Fuera de alcance

- Render interpolation between steps (a separate issue; entities keep their zero-copy `position === node.position` outside projection, `entity.ts:24-26`). At 120 Hz and above the picture updates 60 times a second: accepted.
- Retuning any game-feel value in the three archetypes or the examples.
- Renaming `frames` to `steps` in the bridge or the MCP; changing the `frames` bounds.
- Compatibility with projects or CLIs built before this change; a protocol version bump.
- A per-project or per-`GameOptions` step size.
- #69 (spatial queries), #70 (collision layers), #71 (timers/tweens), #74 (camera effects).
- Changes to the Component Update Schedule (ADR 0004); it runs in full inside each step.
- The version bump and the release itself (`/publish`), a `CHANGELOG.md`, GitHub Releases.

## Riesgos y gaps

- **Float boundaries in CA-1.** 144 deltas of 6.944 ms do not sum to exactly 1000 ms; the criterion advances past 1000 ms on purpose so the 60th step is unambiguous. The implementation must not compare with an epsilon that would let a 61st step in.
- **`simulationTime` is derived, not summed** (inference 6): `3 × (1/60)` and `60 × (1/60)` are exactly `0.05` and `1` in IEEE doubles, which is what `runtime-e2e.mjs:419` and CA-6 assert; summing would drift.
- **Uncommitted grill artifacts.** `CONTEXT.md`, `docs/adr/0014-…`, the note in `docs/adr/0006-…` and `.sdd/grills/2026-09-12-fixed-timestep.md` are in the working tree. `/sdd-run` should carry them into the worktree baseline with explicit approval, as it did on 2026-08-29.
- **`'fixed-step'` is announced, not gated.** The MCP session manager does not check for it (`runtime-session-manager.test.ts:30,304` mock capabilities freely); gating is out of scope and would only matter for old engines, which are a non-goal.
- **Editor coverage is indirect.** `Viewport.tsx:407,425,739` runs the same `Game.start()`; nothing beyond `pnpm build` and the engine tests observes the editor's play mode.
- **e2e needs a compatible Chrome** (contract `## Ambientes`); missing Chrome is red, never a skip.
- **Contract age.** `.sdd/project.md` predates 0.10–0.13 (audio, scene swap) but every command this spec needs is verified; a `/sdd-init --update` after this feature is advisable, not blocking.
- No `[ASSUMED]` items; no `[NEEDS-INPUT]` items.

## Desviaciones

- **[DEVIATION 2026-09-12] CA-2 / CA-4 worked examples.** The spec's `e = 0.033 → 2 steps, remainder ≈ 0.00033` and the plan's "tick with 33 ms elapsed" contradict the spec's own formula: `0.033 < 2 × (1/60) = 0.0333…`, so 33 ms holds one step with a 16.33 ms remainder (the quoted remainder is negative). The formula is the design decision; the tests use 34 ms (2 steps, remainder ≈ 0.67 ms). No scope change.
- **[DEVIATION 2026-09-12] The non-simulating frame keeps the host's per-frame callback.** The editor's edit mode draws its grid, gizmos and UI preview from `game.onUpdate` with `simulate = false` (`packages/editor/src/editor/Viewport.tsx:544`), which the spec's risk note ("editor coverage is indirect") did not consider — moving host callbacks strictly inside Simulation Steps would have frozen the editor's overlays with no test to catch it. Resolution with the minimum safe bias: while simulating, `game.onUpdate` callbacks run only inside steps with `dt = SIMULATION_STEP` (CA-1 holds at 144 Hz); a frame with `simulate = false` runs zero steps (CA-5 holds), but still runs the host callbacks once, with `dt = SIMULATION_STEP`, and closes the input frame once — exactly what the loop did before this change. No API is added (no render hook, per the grill), and every CA holds literally. Covered by its own test in `game-fixed-step.test.ts`; the human may overrule.
- **Test placement (plan, not spec).** The loop tests live in `packages/engine/src/game-fixed-step.test.ts` rather than `game.test.ts`: with them inline `game.test.ts` reached 1064 lines and the `max-lineas-archivo` policy caps every touched `.ts` at 950. `game.test.ts` keeps only its two seam edits.
