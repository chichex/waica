# 3D scenes simulate with Rapier

A 3D scene (ADR 0027) gets one Rapier world, `@dimforge/rapier3d-deterministic-compat` pinned at 0.21.0, stepped once per Simulation Step (ADR 0014) in a phase after every component's `onUpdate` and before the trigger dispatch. 2D is untouched: it keeps the hand-rolled solver, `Solid`, `DynamicBody` and `Hitbox`, and a 2D scene never creates a world.

The deterministic build is the one whose cross-platform results are a promise of the package, not an accident. It cost 0.42 ms per step with 1000 stacked boxes on the maintainer's Mac and 0.33 ms on the Linux bench host, and a stacked-box scene produced the same position hash on both; the standard build produced the same hash too but does not promise it, and the SIMD build produced a different one. A test pins a 200-box hash that `pnpm test` computes on macOS and on CI's Linux.

The module is a dynamic `import()` made once per Game, by the first 3D scene that loads (the one place in the engine that names the package). A 2D project never downloads the roughly 2 MB of base64 wasm, though a bundler still emits it as one separate async chunk next to the entry, which nothing loads up front. The load counts as a pending asset: `game.assets.status.pending` is one higher while it runs, so Assets Ready, the Run Session's wait and the boot order every example already uses cover it, and `game.ready()` of a Game with a live 3D scene also waits for it and rejects, naming the package, if it fails (the bridge hears `physics-backend-failed`). Steps taken while the module loads run every component update and skip only the physics phase; the bodies are created when it arrives. `GameOptions.physics` is the seam (ADR 0013's pattern): tests pass the real module they initialized once, or a rejecting stub.

The model is Rapier's. `Collider` is a shape (box, sphere or capsule, with an explicit size, never derived from a `Model`) and alone it is a fixed wall or floor; beside a `RigidBody` it is the body, `dynamic` (Rapier's: after each step the engine writes its position and rotation to the entity) or `kinematic`. A kinematic body always moves through Rapier's `KinematicCharacterController`: the engine integrates its vertical velocity (the controller applies no gravity), a motor sets its `desiredVelocity`, and it climbs steps, stops at walls, snaps to the ground and pushes dynamic bodies. `Collider{sensor: true}` is the 3D Hitbox: it reuses ADR 0016's layer, mask and directional interest and fires `onCollide` every step while it overlaps another collider; solid contacts reach the new `onBodyContact` hook, leaving the 2D `onContact(SolidContact)` alone. The scene's `simulation.gravity` block (default `[0, -9.81, 0]`) and a per-body `gravityScale` set the fall. `game.query` gains 3D forms of all four operations (ADR 0015's domains kept: `ray` reads solids, `area` and `point` read sensors, `nearest` reads transforms) and refuses the other space's form. The Runtime Snapshot carries a `physics` section in a 3D scene.

A component declares its space on its class (`static space`: `'2d'`, `'3d'` or `'both'`), and `validate_project` reads that marker, so the 2D behavior motors that collide on x/y stop validating clean in a 3D scene.

## Considered Options

A hand-rolled 3D solver mirroring the 2D one was rejected: boxes that stack, topple and bounce are the point of a 3D scene, and that is a physics engine's job; `components/solid.ts` had said the genre character controllers stay hand-rolled for determinism, which the deterministic build and the hash test now answer. The SIMD build was measured faster (0.33 ms against 0.42) and rejected because it changes the hash and promises nothing across platforms. A static import was rejected because every 2D project would carry the wasm. Reading the module through `game.ready()` alone was rejected because a Run Session never calls it; the asset counter reaches hosts, the bridge and scene swaps. A `character` flag choosing the controller was rejected: a kinematic body that passes through geometry is something no author expects.

## Consequences

`@waica/engine` and `@waica/cli` depend on the package (exactly pinned, so an API change between Rapier minors is a deliberate bump, and every file that imports it is in `physics-3d/`). Every bundler of a project that includes the engine emits the wasm chunk, and a project's dev server needs the package installed next to `@waica/engine`, which an install provides. Rapier updates the structure its queries read only inside `step()`, so a zero-second step refreshes it when bodies came or went before a query or a character move. The 3D editor viewport still opens a scene read-only and draws no colliders; navigation, joints, trimesh and cylinder colliders, a follow camera and skeletal animation are later blocks.
