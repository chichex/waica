# Models animate through an Animator the simulation steps

A glTF's clips play through an `Animator` component (issue #166), a sibling of the `Model` that draws the file: it takes the `ModelHandle` the Model already holds (`handle.root`, the entity's own `SkeletonUtils` clone, and `handle.animations`), builds one `AnimationMixer` over that clone and one `AnimationAction` per clip, and advances the mixer by the Simulation Step (ADR 0014) in its `onUpdate`. Nothing runs per render frame and there is no pose interpolation: the pose is a function of the steps taken, deterministic (a test pins an md5 of the rig's bones after 110 steps — mid-swing, never on an identity keyframe — on macOS and on CI's Linux), visible step by step in a Run Session and reported by `inspect_runtime` as `{ loaded, current, time, playing, poseHash }`.

The `StateMachine` stops naming `AnimatedSprite`. It plays through the **Clip Target**: the first sibling that satisfies `isClipTarget` (a `play` function and a `clipNames` member, the duck-typed precedent of the facing provider), which is the `AnimatedSprite` in a 2D scene and the `Animator` in a 3D one. The contract is `{ current, clipNames, clipFinished, clipsPending?, play(name), setFlipX? }`: the directional contract resolves against `clipNames` and mirrors only a target that can. `clipFinished` feeds the new `clip:end` trigger, in both spaces: the target updates after the machine (`updateAfter: ['StateMachine']`, ADR 0004), so the edge fires on the step after a non-looping clip finished and never for a loop (`validate_project` warns `clip-end-on-looping-clip`). The one 2D change is that `play(current)` restarts a finished one-shot instead of staying a no-op, so a state re-entered after its clip ended replays it rather than firing `clip:end` every step. A target whose clips are pending (`clipsPending`: an Animator whose glb is still loading) is asked to play anyway and remembers the request; a target that simply has no clips, like a sprite declaring none, is not pending and still warns.

Playback is authored on the component, not on the states. `fade` (seconds, default 0.15) crossfades from the running action; `0` stops it and plays the new one at once. `clips` is a record of per-clip overrides keyed by the glTF clip name: `loop: false` plays once through `LoopOnce` with `clampWhenFinished`, so the last pose holds like a 2D one-shot sticks on its last frame; `speed` is the action's `timeScale`. `initialClip` plays when the file settles if nothing asked for a clip before. An unknown name warns once and changes nothing; clip names match the file exactly, with the per-state `clip` override mapping lowercase states to a pack's names.

The `Model` keeps only drawing: it now exposes `handle` so the Animator never requests a second handle (a second handle is a second clone), and a rebuild (a new `src` or `shape`) replaces it, which the Animator notices on its next step: it drops the mixer over the old clone and attaches to the new one, asking for the clip it was playing. A `.glb`'s clip names reach `validate_project` through its JSON chunk (`glb-document.ts`: the 12-byte header and the first chunk, a `.gltf` parsed as JSON), so `missing-clip` extends to an Animator's states, `initialClip` and override keys, and an Animator without a Model file is `animator-without-model`, judged per scene entity like the physics composition, since an instance can complete its prefab with a `Model.src` override or an inline Model. In a 2D scene the Animator creates nothing and is a `component-space-mismatch` through `static space`.

Out of this decision, for later blocks: root motion (a clip moves its bones, never the entity), blending layers and blend trees (one action runs at a time apart from the crossfade), retargeting (a clip plays on the file it came from), IK, and a per-state `fade`. Rejected: a per-render-frame hook (it would break the step-exact determinism every other system relies on), an `AnimationObjectGroup` per glb (one mixer per entity keeps clips independent and the fade local), and a `static clipTarget` marker or a `target` param on the machine (a capability the sibling already has is enough to find it).
