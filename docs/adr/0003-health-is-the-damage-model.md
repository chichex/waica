# Health is the damage model, and Hazard only hurts on touch

`Health` in `@waica/behaviors` owns "can be hurt, by how much, and what happens at zero": `max`/`current`, `damage(amount, source?)`, `heal(amount)`, an `invulnerability` window, and the `damage`/`death` events. It is the damage model the workspace had nowhere before — a projectile now targets `entity.get(Health)` instead of borrowing `has(Hazard)` as a stand-in for "enemy". There is deliberately no `kill()`: lethality is arithmetic, so `damage(Infinity)` is the single death path and no second code path can skip the policy.

`Hazard` is narrowed to what its name always claimed — "this hurts the player on touch" — and stops doing both halves of the interaction itself. It no longer destroys itself on a stomp or respawns the player on contact; it routes `stompDamage` and `contactDamage` through whatever `Health` is present. An enemy is `Hazard + Health`, a spike is `Hazard` alone, and a destructible crate is `Health` alone. Each side keeps its exact pre-Health behavior when no `Health` is there to receive the damage, so the change is compatible with prefabs written before it.

The death policy is driven by the state graph, not by `Health`. `StateMachine.signal` is fire-and-forget — it queues into a `Set` and returns nothing, so "destroy it if nobody handled the signal" cannot be answered after the fact. Instead the graph is asked statically: the pure `declaresDeathHandling(states, current)` reports whether a `signal:death` edge exists on the current state or on `'*'` — the same merge `nextTransition` performs. If it does, `Health` signals and stops, and the role decides what death means; if it does not, including an entity with no `StateMachine` at all, the entity is destroyed. The `player` role takes that responsibility: a `'*'` edge into a new `dead` state, which returns to `idle` on a timer and restores spawn and full health on the way out.

`Respawnable` and `OutOfBounds` are split apart. `Respawnable` carried three concepts — remembering the spawn, exposing `respawn()`, and watching a `killY` lower bound — and the third only lived there because its effect happened to be a respawn. With the effect now being damage, watching the world's floor has nothing to do with the component's name, so it moves to `OutOfBounds` (`minY`, default -12), which deals `damage(Infinity)` to anything that can be hurt and destroys anything that cannot. `Respawnable` keeps only what it claims. Rejected alternative: making the bound configurable damage — falling out of the world is lethal by nature, and being hurt by a hard landing is a different mechanic, measured on ground contact, that project code can write with the public `damage()` and the motor's readable velocity.
